RESULTS
PASS: no private-key PEM blocks found
PASS: no Firebase/Google service-account JSON markers found
PASS: no OAuth client-secret patterns found
PASS: no access-token or refresh-token assignment patterns found
PASS: no GitHub PAT/token patterns found
PASS: LCS app.js contains no reads of Firebase user email, provider display name, provider photo URL, or providerData
PASS: v0.5 public writes use authorProfileId/ownerProfileId/followerProfileId/actorProfileId rather than Firebase Auth UID fields
PASS: privateAccounts accepts only publicProfileId, securityVersion, and createdAt
PASS: publicProfiles accepts only displayName, bio, createdAt, updatedAt
PASS: provider photo sharing removed from v0.5
PASS: friend requests / friendships / LFG match requests are private Firestore collections
PASS: owner-only block list added and friend/LFG request rules reject blocked pairs
PASS: legacy v0.4 UID-bearing collections are owner-only for migration and are not public-readable
PASS: CSP and no-referrer policy applied to LCS pages
PASS: user-controlled HTML is escaped before rendering; no eval/new Function/localStorage/cookie application logic found

EXPECTED PUBLIC CLIENT CONFIG
- One Firebase Web App API-key pattern exists in assets/js/config.js.
- This is browser client configuration, not a server secret. It must remain restricted to the intended Firebase APIs/referrers in Google Cloud/Firebase.
- No attempt is made to obfuscate it as a secret.

PUBLIC BY DESIGN
- chosen display name and bio
- posts/comments
- ideas/problems/projects
- communities/channels
- Helpful reactions
- public follows/follower graph
- project/post relationships
- LFG listings
- random public profile IDs

PRIVATE BY RULE
- Firebase Auth UID -> public profile mapping
- block list
- friend requests
- accepted friendships
- LFG match requests

LIMITS
- Firebase Authentication/Google necessarily process authentication data inside their SDK/service boundary. LCS application code intentionally reads only user.uid from the auth callback.
- Users can voluntarily put personal information into any public text field. The UI warns against this; LFG additionally blocks obvious email/phone patterns client-side. Public-post text remains intentionally public.
- Static analysis cannot prove the absence of all future service-side vulnerabilities. Firestore rule deployment is required for the described access boundary to exist in production.
