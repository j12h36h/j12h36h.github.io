DAI 1.9.4

A JSON Game Framework for Minecraft

Decisions and Impulses provides reusable runtime capabilities for building Minecraft games from data. DAI 1.9.4 adds native JSON entities, custom entity AI/hitboxes, layered addons, and player/creator control boundaries on top of the existing client/server game framework.

Current in 1.9.4: native JSON entities and AI, one-main-plus-unlimited-addon loading, expanded player configuration, creator-authored control ceilings, config-aware conditions, automatic old-config migration, and full compatibility with legacy DAI packs.

Engine, Not One Fixed Game Mode

DAI Java Runtime = reusable engine + side-safe execution
Datapack = gameplay, logic, state, world rules
Resource Pack = textures, models, sounds, presentation assets
Creator = visual editor + universal pack/file builder

That means a third-party pack can be a tiny automation, a UI system, a custom content library, or an entire standalone Minecraft experience without requiring experience-specific Java.

Global Datapacks: Main Experiences + Addons

DAI 1.9.4 treats <gameDir>/datapacks/ as a game library with roles instead of assuming every DAI pack competes for the same slot.

Global /datapacks/
├─ MyGame.zip                → MAIN
├─ DamageIndicators.zip      → ADDON
├─ ComicEffects.zip          → ADDON
└─ ordinary_pack.zip         → UNMANAGED

Only one DAI main experience owns a launched game/save. There is no engine-imposed count limit on addons. The launcher builds one combined stack and performs one resource reload.

Role declaration is optional. New packs can use a dai.role field in pack.mcmeta. Legacy DAI packs with an experience or title-screen definition are inferred as main; other legacy DAI content packs are inferred as addons.

Server-Authoritative JSON Actions

DAI 1.8 distinguishes ordinary player commands from actions that require server ownership.

Player authority

run_command behaves like the player typed a normal command. Server permissions still apply.

DAI server authority

server_run_function, server_set_block, server_break_block, server_give_item and server_take_item execute through the DAI server layer when available.

Privileged client-originated mutation is intentionally restricted on dedicated servers. Integrated singleplayer can trust its local DAI client; multiplayer experiences should use server-approved capabilities rather than arbitrary remote privilege.

Client-Only Compatibility

DAI-specific payloads are optional. The client checks whether the connected server negotiated DAI support before sending authoritative requests. If the server does not expose DAI, client automation and presentation can continue operating where they do not require server authority.

Launchable Experiences

Experience definitions can own a save, choose whether to create/load it, select a DAI worldgen profile, define first-join and resume actions, and control experience UI behavior. In 1.9.4 an experience can own the grave/backtick key with explicit open/close actions and an anchor overlay, so a complete game can replace DAI's generic menu cleanly. Worldgen profiles can select a normal Minecraft world preset, seed, spawn, structures, generation commands and bootstrap actions.

Player Preferences + Creator Ceilings

DAI 1.9.4 exposes a deliberately focused set of framework controls: autonomous automation, movement, combat, world editing, action rate, queue size, addon auto-enable, managed resource packs, custom title screens and overlay opacity.

Player Config

Defines the maximum amount of autonomous control and presentation the player permits.

∩

Experience Controls

The main game may restrict automation or lower performance caps, but cannot enable something the player disabled.

"controls": {
  "automation": true,
  "automation_movement": true,
  "automation_combat": true,
  "automation_world_editing": true,
  "max_actions_per_second": 10,
  "max_action_queue_size": 128
}

Older experience definitions omit controls and receive permissive legacy defaults.

Custom Content & Registries

DAI can load datapack-defined content identities for items, blocks, weapons, armor, effects, potions, projectiles, particles, enchantments and entities, plus attributes and animations. Legacy carrier-backed definitions remain supported, while entities may now opt into a fully native DAI physical type.

Native registry content is startup-sensitive. EntityType dimensions and other registry-backed definitions are created during startup. Behavior sequences and other reloadable JSON can still be iterated much more quickly.

Native JSON Entities

A native DAI entity does not need to inherit a Zombie, Skeleton, Spider or other vanilla species class. The datapack defines the real entity dimensions, attributes and behavior sequence; the generic DAI entity engine supplies Minecraft physics, networking and lifecycle integration.

{
  "registry_backed": true,
  "native_registry": "entity",
  "native_attributes": {
    "minecraft:max_health": 30.0,
    "minecraft:movement_speed": 0.28,
    "minecraft:attack_damage": 5.0
  },
  "entity": {
    "category": "monster",
    "width": 1.15,
    "height": 1.35,
    "behavior_sequence": "example:native_hunter_behavior",
    "behavior_interval": 2,
    "vanilla_ai": false
  }
}

DAI 1.9.4 Game Customization Layer

DAI 1.9.4 includes 19 open-ended JSON registries above Minecraft's native data primitives: dai_sounds, dai_music, dai_hud, dai_render_profiles, dai_structures, dai_features, dai_loot, dai_currencies, dai_shops, dai_dialogues, dai_quests, dai_factions, dai_biomes, dai_dimensions, dai_rules, dai_vehicles, dai_interactives, dai_fluids and dai_environments.

Composition instead of duplicate engines. Vanilla-owned structures, features, loot, biomes, dimensions, sounds and entity types remain vanilla resource IDs. DAI definitions wrap them with state, events, actions, functions, commands and presentation so packs remain JSON-driven.
